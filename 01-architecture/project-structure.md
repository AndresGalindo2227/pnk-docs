# Project Structure

`pnk-app` (Ionic + Angular standalone) is organized by **feature**, not by technical type.
Each feature owns its three layers.

```
pnk-app/
├── android/                      Native project generated by Capacitor (versioned)
├── src/app/
│   ├── app.config.ts             Global composition root (providers, interceptors)
│   ├── app.routes.ts             Single route table (see navigation.md)
│   ├── core/                     Cross-feature infrastructure
│   │   ├── di/                   Injection tokens and provideX() functions
│   │   ├── network/              HttpClient setup and interceptors (token, refresh, timeout, errors)
│   │   ├── storage/              Local cache and secure token storage wrappers
│   │   ├── native/               Just-in-time permission helpers
│   │   └── session/              authGuard, guestGuard, current session
│   ├── features/
│   │   ├── auth/                 HU-01, HU-02
│   │   ├── bookings/             HU-03, HU-04, HU-06, HU-07, HU-12
│   │   ├── my-bookings/          HU-05
│   │   └── payments/             HU-09, HU-10
│   │       ├── presentation/     Pages, components, stores (state holders)
│   │       ├── domain/           Entities, ports (interfaces), use cases — no Angular, no Capacitor
│   │       └── data/             Repository implementations, DTOs, mappers, plugin adapters
│   └── shared/                   Reusable UI without business logic
└── src/testing/                  Hand-written test doubles
```

Example — the `bookings` feature:

```
features/bookings/
├── presentation/
│   ├── availability.page.ts
│   ├── booking-confirm.page.ts
│   └── bookings.store.ts
├── domain/
│   ├── booking.ts                 Booking entity
│   ├── time-slot.ts               TimeSlot value object
│   ├── bookings.repository.ts     Port implemented by data/
│   ├── reminder.port.ts           Port for local notifications
│   ├── create-booking.usecase.ts
│   └── cancel-booking.usecase.ts
└── data/
    ├── booking.dto.ts             Mirror of the API JSON
    ├── booking.mapper.ts          toBooking(dto)
    ├── bookings-http.repository.ts
    └── local-notifications.adapter.ts
```

## Rules

- One feature = one folder under `features/`. No cross-feature imports; share through `core/` or `shared/`.
- `shared/` holds only reusable UI. Business logic and use cases never live there.
- No feature reaches into another feature's `data/` or `domain/`.
- Only `data/` adapters import Capacitor plugins; only `core/di/` knows which adapter implements each port.
- A file declares one primary type; the file name matches it.

## Naming

| Thing | Convention | Example |
|-------|------------|---------|
| Feature folder | `kebab-case` | `my-bookings/` |
| Class / type | `PascalCase` | `CreateBooking`, `BookingsRepository` |
| File | `kebab-case.role.ts` | `create-booking.usecase.ts`, `bookings.store.ts` |
| Test | same name + `.spec.ts` | `create-booking.usecase.spec.ts` |
| Test name | `unit_condition_result` | `createBooking_slotInThePast_rejectsWithoutCallingRepository` |

The admin portal (`pnk-portal`) follows the same feature/layer layout for its own features
(`schedule`, `receipts`, `fields`).
